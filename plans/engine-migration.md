# План миграции движка распознавания PDF: pymupdf → pdfplumber

## Цель
Заменить движок извлечения таблиц из PDF-спецификаций с `pymupdf` на `pdfplumber`,
сохранив совместимость интерфейса `pdf_spec_to_row_list(pdf_path)` и всего нижележащего
пайплайна (детекция шапки, `detect_pattern`, `correct_row`, `normalize_row`,
запись в XLSX). Результат должен совпадать с текущим на эталонных PDF, включая
«проблемные» файлы из `test_data/Проблемные/1`.

## Различия API движков

| Операция | pymupdf (сейчас) | pdfplumber (план) |
|---|---|---|
| Импорт | `import pymupdf` | `import pdfplumber` |
| Открытие | `with pymupdf.open(pdf_path) as doc` | `with pdfplumber.open(pdf_path) as pdf` |
| Страницы | `for page in doc` | `for page in pdf.pages` |
| Поиск таблиц | `page.find_tables()` (итератор, у табл. `.extract()`) | `page.find_tables()` (список `Table`, у табл. `.extract()`) |
| Настройка детекции | встроенные эвристики | `table_settings` (`vertical_strategy`, `horizontal_strategy`, `min_words_vertical` и т.п.) |
| Значение пустой ячейки | `None` | `None` |
| Многострочный текст ячейки | текст с переносами | текст с `\n` (аналог) |

## Изменяемые файлы

1. `requirements.txt` — заменить `pymupdf>=1.28.0` на `pdfplumber>=0.11.0`.
2. `libs/spec_pdf_to_xlsx.py`:
   - заменить импорт;
   - переписать `pdf_spec_to_row_list` (открытие через `pdfplumber.open`, итерация `pdf.pages`);
   - в `parse_spec` использовать `page.find_tables()` / `tab.extract()` без изменения
     остальной логики строк (детекция шапки, `template_cols_count`, `detect_pattern` и т.д.);
   - при необходимости добавить `table_settings` для корректного распознавания
     «проблемных» файлов;
   - **временно** сохранить старые функции (`parse_spec_pymupdf`, `pdf_spec_to_row_list_pymupdf`)
     под другим именем для A/B-сравнения (импорт pymupdf — опциональный, чтобы не мешал
     продакшену после удаления зависимости).
3. `app.py` — обновить комментарий «нужен pymupdf» (косметика).
4. `scripts/compare_engines.py` (новый) — скрипт прогона старого и нового движка по
   папке PDF с выводом diff спецификаций; запускается в режиме Code или вручную,
   т.к. `test_data` исключён из доступа инструментов.

## Реализация

Файлы, изменённые/созданные:
- `requirements.txt` — `pymupdf>=1.28.0` → `pdfplumber>=0.11.0`.
- `libs/spec_pdf_to_xlsx.py`:
  - импорт `pdfplumber` вместо `pymupdf`;
  - `pdf_spec_to_row_list()` открывает документ через `pdfplumber.open(pdf_path)` и
    передаёт `pdf.pages` в `parse_spec()`;
  - `parse_spec(pages)` принимает итерируемый объект страниц (единый для обоих движков);
  - добавлена `_decode_cell()` — постобработка ячеек, восстанавливающая символы из
    артефактов pdfplumber/pdfminer вида `(cid:N)` (проблема нестандартных GOST-шрифтов
    без корректного ToUnicode CMap).
- `libs/utils.py`:
  - исправлен `normalize_row()` — результат очистки (`\n`→пробел, схлопывание пробелов,
    `strip`) теперь записывается обратно в `spec_line` по индексу (раньше менял только
    локальную переменную цикла);
  - `row_list_to_md()` — безопасный `join` с приведением значений к `str()`.
- `app.py` — косметика комментария «нужен pymupdf» → «нужен pdfplumber».
- `test_pdf_spec.py` — исправлены импорт `row_list_to_md` (из `libs.utils`) и распаковка
  кортежа из `pdf_spec_to_row_list()` (раньше тест был сломан).

Убрано после проверки: временная функция `pdf_spec_to_row_list_pymupdf()` и
`scripts/compare_engines.py` (A/B-инструмент миграции).

## Результаты проверки (A/B: pdfplumber vs pymupdf по test_data)

Прогон сравнения по всем PDF в `test_data` (13 файлов):

- **10 файлов — полное совпадение** результата `(spec, template_cols_count, restored_rows)`,
  включая все `archive/*` и большинство «обычных» спецификаций.
- **«1102-10UTA…10 столбцов»** — после внедрения `_decode_cell()` совпадает (121 строка).
  Без постобработки pdfplumber выдавал `(cid:26)`, `(cid:49)` и т.п. Вмешательство
  `table_settings` не требовалось — проблема была на уровне извлечения текста шрифта.
- **«321022…ЭП10 v2»** (и копия в `Проблемные/1`) — pdfplumber даёт **22 строки против
  17 у pymupdf**: позиции 3.3–3.7 («Гайка М12», «Болт М20х100» и др.), которые pymupdf
  терял, pdfplumber распознаёт. Это **улучшение полноты**, а не регресс.
- **«Спека ТР4.1»** — одинаковое число строк (686). Единственное отличие — в одной длинной
  ячейке исходник разбит словами через `_`/пробелы: pdfplumber `512GB_PCIe_M.2`,
  pymupdf `512GB PCIe M.2` (плюс лишние `_ _ _ _`). Косметическая разница форматирования,
  содержание эквивалентно.

Вывод: миграция выполнена без потери данных. Для файла с нестандартным шрифтом качество
сохранено за счёт `_decode_cell()`; в ряде случаев pdfplumber распознаёт даже полнее pymupdf.

## Ожидаемый результат (достигнут)
- `pdf_spec_to_row_list(pdf_path)` возвращает кортеж `(spec, template_cols_count, restored_rows)`;
- pymupdf полностью исключён из зависимостей и кода (в коде проекта ссылок нет);
- спецификации из `test_data` распознаются корректно, включая «проблемные» файлы.
